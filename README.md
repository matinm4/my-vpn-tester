# V-Tester — نسخه‌ی گیت‌هاب اکشن

نسخه‌ی لینوکسی تستر کانفیگ‌های Xray. هر ۳۰ دقیقه ۲۰ کانفیگ برتر را بازبینی
می‌کند و هر ۶ ساعت یک دور کامل از تلگرام + لینک‌های ساب می‌گیرد — همه بدون
اینکه کامپیوتر شما روشن باشد.

> این نسخه از روی پروژه‌ی ویندوزی ساخته شده. نسخه‌ی اصلی (`run.py` / `live.py`)
> که با `xray.exe` محلی کار می‌کند در مخزن اصلی است.

## این نسخه چه فرقی دارد

| | نسخه‌ی ویندوزی | نسخه‌ی گیت‌هاب اکشن |
|---|---|---|
| اجرا | دستی / Task Scheduler | خودکار با cron |
| تلگرام | نیاز به فیلترشکن + دروازه | بدون فیلترشکن، ساده |
| حافظه | `.cache/configs.db` محلی | شاخه‌ی `data`، رمزنگاری‌شده |
| خروجی | فایل در `output/` | Artifact گیت‌هاب + خلاصه در صفحه |

**کد پایتون هر دو دقیقاً یکی است.** تفاوت فقط در فایل تنظیمات و ورک‌فلوهاست.
ورک‌فلو قبل از اجرا `config.yaml` را از `config.ci.yaml` + سکرت‌ها می‌سازد،
پس `vtester/` هیچ کد مخصوص CI ندارد و به‌روزرسانی هر دو نسخه یکی است.

## راه‌اندازی (۵ دقیقه)

۱. این کد را در یک مخزن **عمومی** جدید پوش کنید.

۲. سکرت‌ها را تنظیم کنید (Settings → Secrets and variables → Actions):

   | سکرت | لازم؟ | چیست |
   |---|---|---|
   | `VT_STATE_PASSPHRASE` | ✅ حتماً | رمز رمزنگاری حافظه — هر رشته‌ی بلندی |
   | `VT_TELEGRAM_API_ID` | برای تلگرام | از my.telegram.org |
   | `VT_TELEGRAM_API_HASH` | برای تلگرام | همان‌جا |
   | `VT_TELEGRAM_SESSION` | برای تلگرام | نشست — ساختنش پایین آمده |
   | `VT_TELEGRAM_CHANNELS` | برای تلگرام | مثلاً `@channel1,@channel2` |

   ⚠ `VT_STATE_PASSPHRASE` را بعداً عوض نکنید — حافظه‌ی قبلی دیگر رمزگشایی
   نمی‌شود و سرویس از صفر شروع می‌کند.

۳. تب **Actions** را باز کنید. «بازبینی استخر» را با «Run workflow» دستی
   اجرا کنید تا همه چیز از اول کار کند.

۴. لینک‌های ساب خودتان را در `subs.txt` بگذارید (هر خط یک لینک). اگر
   `subs.txt` را در مخزن نگذارید، مخفی می‌شود چون توکن‌ها در آن‌اند.

## ساختن session_string تلگرام

یک بار روی سیستم خودتان (پایتون + `pip install telethon`):

```python
from telethon.sync import TelegramClient
from telethon.sessions import StringSession

client = TelegramClient(StringSession(), API_ID, "API_HASH")
client.start()            # شماره + کد تأیید را می‌پرسد
print(client.session.save())
```

رشته‌ی چاپ‌شده را در `VT_TELEGRAM_SESSION` بگذارید.
**هرکس این رشته را داشته باشد به حساب شما دسترسی کامل دارد.**

اگر این سکرت‌ها را تنظیم نکنید، تلگرام خودکار خاموش می‌شود و سرویس فقط از
`subs.txt` کار می‌کند.

## خروجی‌ها

هر اجرا خروجی‌ها را به عنوان **Artifact** نگه می‌دارد (۹۰ روز):

```
output/
  top20.txt          ← ۲۰ کانفیگ برتر، لینک خام
  top20_sub.txt      ← همان به base64 — برای import در کلاینت
  batches/batch_01.txt ...   دسته‌های ۲۰تایی
  report.html        ← گزارش کامل
  results.json       ← داده‌ی خام
```

خلاصه‌ی هر اجرا هم در خود صفحه‌ی اکشن نمایش داده می‌شود.

### لینک عمومی

کانفیگ‌ها در شاخه‌ی `public` هم منتشر می‌شوند تا با یک لینک ثابت در هر
کلاینتی import شوند و خودکار به‌روز بمانند:

```
https://raw.githubusercontent.com/USERNAME/REPO/public/top20_sub.txt
```

۲۰ برتر در یک فایل، باقی کانفیگ‌های سالم در `batches/`. جزئیات در
[SETUP.md](SETUP.md#گرفتن-خروجی).

نام هر کانفیگ پیش از انتشار بازنویسی می‌شود به `🇩🇪 DE-01 | 210ms`، چون نام
اصلی منابع عمومی معمولاً آی‌دی تلگرام یا متن تبلیغاتی است. آدرس، پورت،
UUID و بقیه‌ی فیلدهای کارکردی دست‌نخورده می‌مانند.

## امنیت

- **پایگاه داده (حاوی UUID و رمز کانفیگ‌های سالم) رمزنگاری‌شده** در شاخه‌ی
  `data` ذخیره می‌شود. بدون `VT_STATE_PASSPHRASE` هیچ‌کس نمی‌تواند آن را
  بخواند — حتی صاحب مخزن.
- `session_string` فقط در سکرت است. ورک‌فلو موقع اجرا `config.yaml` را
  می‌سازد و آن فایل با پایان job از بین می‌رود؛ هرگز کامیت نمی‌شود.
- `config.yaml` در `.gitignore` است تا اشتباهی پوش نشود.
- شاخه‌ی `public` عمدی عمومی است: کانفیگ‌های سالم آنجا برای همه قابل دیدن‌اند.
  نام منبع (کانال تلگرام / تبلیغ) قبل از انتشار حذف می‌شود، ولی خود کانفیگ‌ها
  عمومی می‌شوند. اگر این را نمی‌خواهید مرحله‌ی «انتشار عمومی» را از ورک‌فلوها
  بردارید.

## ساختار

```
.github/workflows/            discovery.yml و pool-refresh.yml
.github/actions/setup-xray/   دانلود هسته‌ی لینوکسی
scripts/make-config.sh        ساخت config.yaml از سکرت‌ها
scripts/state.sh              ذخیره/بازیابی رمزنگاری‌شده‌ی حافظه
scripts/publish.sh            انتشار کانفیگ‌ها در شاخه‌ی public
scripts/summary.sh            خلاصه‌ی نتیجه در صفحه‌ی اکشن
config.ci.yaml                الگوی تنظیمات CI (بدون رمز)
vtester/                      کد اصلی — دقیقاً مثل نسخه‌ی ویندوزی
```

## اجرا

- **`discovery.yml`** — هر ۶ ساعت، دور کامل (سنگین، تا ۲ ساعت)
- **`pool-refresh.yml`** — هر ۳۰ دقیقه، فقط بازبینی استخر (سبک، چند دقیقه)
- هر دو از تب Actions با دست اجرا می‌شوند.

### محدودیت مخزن عمومی

گیت‌هاب برای مخزن عمومی ۲۰۰۰ دقیقه در ماه رایگان می‌دهد. با زمان‌بندی فعلی
(حدود ۵۰ اجرا در روز × میانگین ۵ دقیقه) مصرف تقریباً ۲۵۰ دقیقه در ماه است —
خیلی کمتر از سقف.

### چرا دقیقاً ۳۰ دقیقه نیست؟

زمان‌بندی گیت‌هاب دقیق نیست: اجراها ممکن است تا ۱۵ دقیقه تاخیر داشته باشند،
مخصوصاً در ساعات شلوغ. برای یک استخر ۲۰تایی این تفاوت مهم نیست.
